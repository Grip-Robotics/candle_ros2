## Subsequent software change: minimum closing-command torque

After reviewing the foil results, the operator requested a 0.25 Nm minimum
closing torque, without changing endpoint recognition or replacing higher
timeout holds with the light bias. The shared controller now uses the existing
`gripper_closed_hold_torque_nm` setting as its closing-command floor as well as
its settled-closed hold, clipped to the existing caps. Approach commands whose
sampled PD + I sum falls below that floor use pure floor torque; higher-effort
PD + I commands are unchanged. Recovery/startup no longer inserts a zero-effort
closing command, and timeout captures are bounded by the floor. Opening,
fault/disable behavior, targets, guards, gains, zeros and the 2 Nm object target
are unchanged. This is a sampled command bound, not a guarantee of minimum
instantaneous measured torque; below-floor closing PD braking is replaced by
the floor, so physical closing dynamics require revalidation.

Fresh isolated Jazzy and Humble builds/tests passed: 45 C++ test cases plus the
recorder self-test on each (colcon reports 49 entries including suite wrappers).
`git diff --check` passed. No motor was enabled and no physical trial used this

### Confirmed cause and change

Temporary readback tracing, without changing the original 10 ms deadline,
showed successful reads of **state 7 / mode 8** during braking. Two closing
stops completed in approximately 7–9 ms. A fast-opening stop at 0.569951 rad,
-11.1935 rad/s exceeded the deadline, including subsequent cleanup attempts.
There was no failed read or fault-state bit: normal quick-stop was incorrectly
reported as communication loss. That false recovery also produced a spurious
position-reference ambiguity while the motor was still moving. All three
were subsequently verified disabled by the exclusive read-only SDK probe.

Read-only register inspection found `quickStopDeceleration = 100` on all
three drives, with `canWatchdog = 100 ms`. The observed longer braking phase
is consistent with that setting and the
[MD state machine](https://mabrobotics.github.io/MD80-x-CANdle-Documentation/MD/state_machine.html).
Simply blocking the single-threaded ROS node for a longer stop wait would
also delay feedback/control and the other motors' watchdog traffic.

The shared disable transition now requests the stop once, immediately cancels
the motion job and inhibits subsequent motion, then checks for **actual
disabled state** asynchronously through the existing joint-state timer. The
confirmation deadline is 500 ms, not a successful-stop fallback. Normal
braking preserves position tracking; only failed transfers initiate position
recovery. Fault/refused/expired transitions return failure and remain inhibited.
The disable service defers its reply until confirmation or failure and retains
each result until a multi-ID request is complete. Pending stops reject init,
enable, zero and configuration. Setup retains its short 10 ms fast path; if
braking takes longer, setup fails safely and must be explicitly retried after
the asynchronous stop. Shutdown requests all stops before waiting for any one
motor. Init/zero failure cleanup uses the same stop path. Tracing was removed.
